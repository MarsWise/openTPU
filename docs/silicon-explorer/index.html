Inside one openTPU slice

The board target uses S = 1. The general RTL also supports multiple slices with a collective unit. Issued instructions can overlap across units: the scoreboard tracks dependencies.

TMEM, ACT RAM and DRAM are distinct. The real design has no conventional data cache; movement is explicit and instructions communicate through known memory footprints.

Systolic MXU · from a weight chunk to a dot product

D = 128 products per column, one 128-byte chunk streamed from DRAM, with stationary activation rows in ACT RAM. Four physical compute columns in the default m4 target. m8 is a separately selectable build variant, not a claim that it is the card's loaded image.

    The original INT8/FP4 path and branch-specific ternary TMM/GSC path have different throughput and data movement. Do not treat 512 MAC/cycle as the sustained single-token TMM throughput.

    Vector pipeline · eight FP32 lanes

    LANES = 8, with VPU_CL = 2 long composite-function lanes in the default m4 target. VPU and MXU are separate units in openTPU; this is not Esperanto's shared tensor/VPU implementation.

    Instruction → concurrent hardware units

    The compiler emits eight 32-bit words per instruction. The sequencer decodes instructions in order but dispatches independent work into a scoreboard window. Each unit has its own ready/busy handshake.

    What this project does not do

    • It does not reproduce the original Esperanto/Spacesheep site's HTML, artwork or deep zoom.
    • It is a logical architecture diagram, not a routed Vivado physical floorplan.
    • It is not a live FPGA monitor and does not parse .otpuprof files; use otpu-lens for traces.
    • It does not claim that feature-branch RTL changes are loaded on the user's FPGA card.
    • It cannot certify current Vivado timing or power without an actual build and board measurement.
