## 4. What the user does (the build)

1. Stop any running Vivado build.
2. Run `C:\myOpenTPU\_claude\r5m8_next.cmd`. It
   - refuses if the worktree has tracked changes;
   - fast-forwards the worktree from `sync.bundle` (no merge, no push);
   - synthesizes the MXU out of context into `_claude\mxu_check_<rev>\` (~20-30 min);
   - only if LUT <= 75,000 and 0 latches: `tools\build_r5_timing.ps1 -Mode Build -Jobs 24`
     (m8, 150 / 300 MHz, the fence on), output `build\vivado-r5-timing-<rev>\` (several hours);
   - log: `_claude\r5m8_next.log`. Never programs the FPGA; no bitstream unless WNS and WHS >= 0.
3. Send back: `r5m8_next.log`, `build\vivado-r5-timing-<rev>\reports\SUMMARY.txt`,
   `reports\stages\placed\timing_summary.rpt` + `timing_worst.rpt` (as soon as placement ends:
   it decides whether to wait for routing), and at the end `full.log`'s tail. With many failing
   endpoints: `_claude\r5_paths.cmd` (read-only path analysis of the placed checkpoint).
4. A bitstream is not loaded without the user's explicit "да" (JTAG, volatile).
