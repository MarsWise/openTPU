# Handoff 15.11.2026 — ошибка MXU в r7/r8, работа Codex, Needle

Дополняет `HANDOFF_2026-11-10.md`. Измерения: `VERIFIED_RESULTS.csv`, строки `c9f51ceb+`.

## 1. Главное: в битстриме r8 `2c800a8f` ошибка MXU, нужна пересборка

- **Что.** `otpu_mxu` с коммита `6df6a665` (31.10, TMM GRQ) отбрасывал бит 4 смещения блока шкал `k0`
  у обычного MM (бит 28 слова w4 — флаг GRQ у TMM). MM, начинающийся с блока 16..31 mod 32, читал
  шкалы блока `k0 − 16`. Ошибка во всех сборках r7 и в r8 `2c800a8f`. В r5 `45b1c1d3` её нет.
- **Когда проявляется.** MM по int8 / 4-битной матрице с поблочными шкалами, когда операнд состоит из
  нескольких диапазонов QACT или матрица нарезана по столбцам, и часть начинается дальше 15-го блока
  (K > 2048 при D = 128). RSC, UNIT и все TMM (BitNet, Bonsai) не затронуты.
- **Кто нашёл.** Codex (`37e9e702`), он же свёл к этому давно падавший
  `test_waitc_rtl_hazard_stress[3]`. В ветке — вариант, где биты TMM оставлены как были.
- **Проверка.** Verilator 5.046: новый тест `test_mm_block_offset_uses_all_eight_bits`, четыре
  `test_waitc_rtl_hazard_stress`, `test_tmm_t5` (RTL) — все прошли. Полный набор RTL-тестов на
  исправленном RTL НЕ прогонялся (в контейнере 1 ГБ диска).
- **Защита на старых битстримах.** `board.MM_K0_ERRATA = {0x2c800a8f}`: `load_program` отказывает
  программе с таким MM (`ConfigMismatch`, «k0 bit 4»). Если модель на r8 `2c800a8f` теперь
  останавливается с этой ошибкой — её прежние числа на карте были неверны. Сборки r7 в список не
  внесены (их BUILD_ID нет в `firmware_contract.json`).
- **Что делать.** `_claude\r8\r8_build_k0fix.cmd` (полная сборка, несколько часов, ничего не
  грузит). После сборки: sha256 и BUILD_ID в `firmware_contract.json`, `r8_load.cmd <путь к bit>`,
  `r8_restore_pcie.cmd`, `r8_card_tests.cmd` (в нём теперь есть случай «MM k0 scale offsets»).

## 3. DDR на r8: что известно теперь

- После калибровки под нагрузкой (`ternary:4`) прогон r8 10.11 в 20:30 дал 17 из 17, ECC 0/0 на
  каждом шаге. До этого на r8 были SEC и один раз DED. То есть r8 не «сломана», а на грани: зависит
  от калибровки. Длительной проверки нет.
- Размещение (Codex): вычислительных примитивов в регионах X0Y0–X0Y2 (канал 0) у r8 69 669, у r5
  23 860.
- Тайминг (этот сеанс, по сохранённым отчётам): группа `sys → writeclocks0_outs2` (данные записи
  канала 0) — запас r8 +0,229 нс, r5 +1,983 нс. Худшие пути r8 идут от
  `u_ld/wl7ddrphy0_bitslip0_r0_reg[8,10]` в SLICE_X4Y307 (область канала 1) к OSERDES канала 0 в
  Y20: 6,1 нс трассы. Этот регистр после калибровки не меняется, так что сам он ошибок давать не
  должен; запас по динамическим путям данных из отчёта не виден.
- `otpu_ddr_phy_place.tcl` закрепляет у пинов только триггеры, которые идут в OSERDES напрямую
  (404 шт.). Данные DQ идут через LUT (выбор bitslip), их триггеры размещает Vivado.
- Причина ошибок не доказана. Проверка без пересборки: `set PASSES=4` и `r8_ddr_check.cmd`
  (те же случаи четыре раза подряд без перекалибровки; критерий — 0/0 в каждом проходе).
- Для пересборки: сначала собрать с исправлением MXU без изменений размещения и повторить
  `r8_ddr_check`. Менять размещение имеет смысл, только если ошибки останутся.
