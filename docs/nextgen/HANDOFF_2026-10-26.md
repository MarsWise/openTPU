## 4. The open problem: DDR3 channel 0 ECC errors under some device traffic

Facts (PHYSICAL):
- Errors on **channel 0 only** (channel 1: 7 corrected in a whole evening). Uncorrectable ones
  (STATUS ECC_DED) stop runs; later runs are unchecked until the counters are cleared.
- Clean: host DMA pattern tests (idle and under loadcal's fp4 and TMM loads); loadcal's loads;
  one BitNet sequence's resident decode (0 of 32 runs, many 128-token runs).
- Failing: batch.py steps (2 rows 7-17 of 32 runs with errors, 4 rows 5-7 of 32), run_rows
  4 rows (1-2 of 16), Qwen3.5-2B fp4 (first ECC_DED of models_r5), the evening's models stage
  2,084 corrected / 583 uncorrectable on channel 0.
- Not the cause: the read taps (loadcal under fp4 and TMM loads: the same windows, channel 0
  3-5 taps, channel 1 3-5); the host recalibration (`memcal cal --force`: channel 0 write window
  636 ps against channel 1's 1,105 ps, unchanged; errors the same); the batched steps' picks
  sharing an ECC word (one beat a row since c4b6e989; errors remained).
- Channel 0's common write window is the narrow one (636-653 ps vs 1,105 ps).

Open hypotheses:
1. **Logic**: `rtl/shell/otpu_mem_ch.sv`'s read-modify-write of partial beats (the board has no
   DM pins; every store of less than a 64-byte beat is read, merged, written) racing another
   access to the same beat.
2. **Physical**: channel 0's write margin, with the device's stores (many read/write
   turnarounds among streamed reads) where host DMA writes long bursts.

Decider (prepared, not run): `_claude\rmw_check.cmd` -> `tools/ddr_diag.py rmw` twice: streamed
loads with no store / a whole beat / a partial beat / two partial stores to one beat / a 64 KiB
tile stored back, per channel, ECC per case (~5 min).
- errors only with partial beats -> fix `otpu_mem_ch`'s RMW ordering (r6 RTL) and make the
  compiler avoid partial beats where cheap (pad small stores to a beat);
- errors with whole beats / tile stores too -> physical: try `r5m8_133.cmd` (core = controllers'
  clock), then channel 0's write side in two groups (docs/litedram.md "Groups": group 0 lanes
  0-3 bank 11, group 1 lanes 4-8 banks 12-13; estimated 78 / 40+ steps against 38 as one group;
  the earlier DRP-offset attempt failed, so this is calibration / PHY work).

Until resolved: trust outputs only where ECC stayed 0 / 0 (`tools/ddr_diag.py` and the card
scripts print the counters per case).

## 8. How runs work here

- Windows `C:\myOpenTPU\_claude\*.cmd`: each copies `sync.bundle` + its `.sh` to the host,
  fast-forwards `~/openTPU_BitNET`, runs under `/tmp/claude_run.lock` (one run at a time; a
  second start says "another claude run is in progress"), and copies the log back. Host results
  also stay in `~/openTPU_BitNET/runs/<name>-<time>/`.
- Python envs on the host: `.venv` (card tools), `~/hfref` (transformers), `~/vllmenv312`
  (vLLM 0.32.0), `~/lrenv312` (LeRobot; diffusers installed by models_r5).
- Delivering files to Windows from a cloud session: write under a new name, copy over on the
  device and compare sha256 (an existing name may keep a stale copy).
