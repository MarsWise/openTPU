### Софт (всё с тестами, результат совпадает со старым путём бит в бит)
- `resident.Graph`: поэлементные операции и `linear` режутся на блоки строк; attention режется на программы (KV отдельно, запросы по блокам), размер каждой программы измеряется и делится, пока не влезет в IMEM.
- `qwen3._bitnet_mlp`: при многих строках gate / up считаются кусками по F, большой тайл выделяется первым (TMEM разделена пополам дескрипторами STREAM).
- `batch.Steps.feed`: при нехватке TMEM подаёт промпт меньшими порциями.
- `loadcal`: нагрузка `int8[:rows]`; в тесте платы по умолчанию `ternary:4`.
- `vllm_smoke`: эталон для сэмплирования на картах с VRAND (ключ — первое число генератора запроса, равномерное число — по позиции токена).
- `tools/tourney/gen_components.py` снова парсится; `otpu_rand.sv` в компоненте VPU.

## 3. Главная открытая проблема: DDR3 на r8

Факты (всё на плате, 10.11):
- На r8 под тяжёлой нагрузкой (vLLM BitNet 4 слота, `run_rows` с int8-головой) есть ошибки ECC. Без `loadcal` — сотни, с неисправимыми; с `loadcal ternary:4` — единицы исправленных, изредка неисправимая. Калибровки fp4, int8:4, ternary:8 не лучше.
- **Исправленные ошибки не безвредны:** в прогоне 18:44 vLLM greedy дал неверные токены при 0 неисправимых. Правило: шаг с любым ненулевым счётчиком не засчитывается.
- `ddr_diag rmw` (полные, частичные, двойные частичные записи) чистый всегда: логика записи `otpu_mem_ch` не виновата.
- **Решающий опыт (19:46–19:58): на той же плате прошивка r5 `45b1c1d3` (те же 133.33 МГц, тот же PHY и настройки) даёт ECC 0/0 во всех этих случаях**, в том числе без `loadcal`: rmw, все режимы декодирования BitNet, vLLM 4 слота PASS 22.9 ток/с. Плата исправна; причина в прошивке r8.
- Разница в калибровке: общее окно записи канала 0 — 753 пс на r5 против 653 пс на r8; окна чтения под нагрузкой 4–6 шагов против 2–5.

Вывод: r8 (на 15K LUT плотнее) ухудшает запас DDR — шум или размещение рядом с PHY. Колонки MXU те же, что у автора (X3–X10).

**Что делать (по порядку):**
1. Сравнить размещение r8 и `45b1` около банков DDR (11–13 для канала 0): что из логики ядра встало рядом с PHY / IDELAY / BUFIO. Оба `dcp` есть на Windows.
2. Пересобрать r8 с запретом размещения логики ядра рядом с PHY канала 0 (pblock с отступом), при необходимости с отдельным размещением новых блоков r8.
3. Проверить новую сборку тем же `r8_ddr_check.cmd` (критерий: 0/0 во всех случаях, как у `45b1`), затем `r8_card_tests.cmd`.
4. Только если не поможет: ODT / сила драйвера (MR1 / MR2) — запись в регистры памяти, нужно отдельное согласие пользователя.

## 4. Что не сделано по ТЗ

**Железо и приёмка**
- ECC 0/0 под длительной нагрузкой (раздел 3). Пока не закрыто, большие LLM на r8 не принимаются.
- Полный sign-off CDC / bus skew.
- Скорости на r8 не измерены (perf.py для Qwen / LFM, BitNet одиночный); COCO-500 для YOLOX на r8.

**FPGA-only runtime**
- Автономное исполнение графа на карте. Сейчас хост запускает программы по одной: SmolVLA base — 12 948 запусков, 402 с при ~10 с счёта на карте; pusht 100 шагов — 10 790 запусков. Нужно сцеплять программы на карте (HALT CHAIN / таблица программ в DDR).
- Планировщик памяти для нескольких моделей; единый strict-аудит с негативными тестами; первый токен MTP на карте, k > 1; MoE без хоста.

**Модели**
- Только ISA, на плате не запускались: LFM3 (ещё нет кольцевого KV), MiniCPM5, Granite, Ouro 1.4B, Dory, Needle (есть и RTL), PaddleOCR-VL, MiniCPM-V. Веса лежат на Windows в `ai-models`, на хосте их нет.
- Не начаты или в начале: MusicGen (веса извлечены в fp16 в `_claude\musicgen_fp16`, папку можно удалить), Kokoro, SD 1.5, Ouro 2.6B, Bonsai 9B, FFN pruning, сверка качества 6-битного KV.
- На хосте есть и на r8 не запускались: Qwen3-0.6B, Qwen3.5-0.8B / 2B / 4B, LFM2.5-230M, LFM2-2.6B, LFM2.5-8B-A1B, gemma-4, SmolLM3, Phi-4-mini.

**Регрессия и документы**
- Падают: `tests/test_waits.py::test_waitc_rtl_hazard_stress[3]` (RTL != ISA, давно) и `tests/test_prefill.py::test_prompt_programs_come_from_the_cache` (102 компиляции вместо 91; было и до правок 10.11).
- `test_bitnet_engine::…matches_transformers` — в контейнере нет `accelerate`.
- Полный набор тестов на текущем коммите не прогонялся.
- Не обновлены под r8: PROGRESS, MODEL_COMPATIBILITY, OPERATOR_COVERAGE_MATRIX, HARDWARE_CONNECTIVITY.

## 5. Как работать с платой

Все скрипты — из `C:\myOpenTPU\_claude\r8\`, в PowerShell с префиксом `.\`.

| Скрипт | Что делает |
|---|---|
| `r8_load.cmd [путь к .bit]` | Загрузка по JTAG без flash; спрашивает `yes`. Перед ней закрыть чаты и прогоны на хосте |
| `r8_restore_pcie.cmd` | Пересканирование PCIe на хосте (sudo), печатает сборку карты |
| `r8_card_tests.cmd` | Шаг 0b (selfcal, обнуление, loadcal ternary:4, selftest), затем инструкции, KV, модели; ECC по каждому шагу. ~15 мин |
| `r8_ddr_check.cmd` | Случаи DDR при калибровках `none` и `ternary:4` (переменная `KINDS` в `.sh`) |
| `r8_chat.cmd <модель>` | Чат: bitnet, bonsai, qwen3, qwen35, qwen35-2b, lfm2; ECC до и после |
| `r8_models.cmd` | Только чтение: модели на хосте, сборка карты |

Особенности:
- После каждой загрузки прошивки DDR надо откалибровать (шаг 0b теста платы), иначе первые чтения дают ошибки ECC.
- Файлы в `_claude` из облачной сессии надо записывать под новым именем и копировать на месте: одноимённый файл может остаться старым. В `sync.bundle` проверять коммит (`head -c 120 | strings`).
- Если `r8_restore_pcie` пишет «the card is in use» — на хосте остался процесс; завершить его (`pkill -f r8_chat_exec.sh`, `kill <pid>`).

## 6. Правила (без изменений)

- Пушить только в `MarsWise/openTPU`, ветка `feature/r7-fpga`. Никогда в FeSens, никогда в main, без force-push; PR #1 остаётся draft.
- Загрузка прошивки, пересканирование PCIe, запись в регистры памяти, запуски Vivado — только с явного согласия пользователя; загрузка только volatile.
- Пароли и секреты в файлы и логи не писать.
- Не смешивать классы доказательств: ISA, RTL, PHYS. «PHYS» — исполнение на плате; приёмка — только при ECC 0/0.
- Только m8. BFLY / AFF / CSWP ради площади не отключать.
